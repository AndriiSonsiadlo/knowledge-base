# Design: Embedded Systems & Bare-Metal documentation section

## Goal

Add a new top-level documentation section covering embedded software engineering from the
electronics a firmware developer must read, up through bare-metal Cortex-M programming, RTOS
work, embedded Linux, functional safety, security, and the firmware product lifecycle.

The section is `docs/embedded/`: **16 numbered folders, 167 topic pages plus a section
`readme.md`**, plus 16 `_category_.json` files, plus a small amount of site wiring (a WaveDrom
remark plugin, one new theme component, one new third-party plugin, four Prism languages).

This document specifies the structure, conventions, and a page-by-page outline detailed enough
that writing the actual `.md` content is a mechanical follow-the-outline exercise.

## Precedent

`docs/gpu-computing/` (129 pages, 14 numbered folders, own sidebar and navbar tab, specified in
`2026-08-13-gpu-computing-docs-design.md`) defines the house style at this depth. This section
follows it: numbered folders, `readme.md` landing page with learning paths, `_category_.json`
per folder, frontmatter shape, admonition vocabulary, `## See also` endings.

Two deliberate departures from the GPU section:

1. **Every page ends with `## References`** — annotated external sources. The GPU section kept
   external links inline; `docs/computer-science/` uses a `## References` block, and that is the
   convention adopted here (see [External references](#external-references)).
2. **The reader is assumed to have no prior hardware experience.** Pages carry explicit
   prerequisites, and folder 01 tells the reader which board and instruments to buy.

## Decisions taken

| Decision | Choice |
|---|---|
| Placement | New top-level section + navbar tab (7th, after GPU & Accelerators) |
| Scope | Full ladder: bare-metal → RTOS → embedded Linux, **plus** functional safety and industrial protocols as first-class folders |
| Organizing scheme | Layer ladder (stack order), one section, with debugging consolidated into folder 11 |
| Hardware spine | ARM Cortex-M (STM32, `arm-none-eabi-gcc` + CMake) primary; RISC-V as a contrast thread, not a parallel folder |
| Languages | C primary; embedded C++ pages; a Rust folder; MicroPython surveyed |
| Timing/register visuals | WaveDrom, rendered to SVG at build time by a custom remark plugin |
| Comparison visuals | `@theme/Tabs` (already available, currently unused in `docs/`) |
| Dense figures | `docusaurus-plugin-image-zoom` (verified compatible) |
| Duplication | Existing pages own their topics; embedded pages link and go deeper. See [No-duplication contract](#no-duplication-contract) |
| Currency | Verified against live vendor documentation via context7 at write time |
| Delivery | Three phases, each its own implementation plan and build gate |

## The WaveDrom integration

### Why it exists

Embedded documentation has two visual needs Mermaid cannot serve: **signal timing** (SPI clock
phase, I2C start conditions and clock stretching, UART framing, CAN arbitration, DMA
half-transfer interrupts, wake-from-sleep sequences) and **register bit-fields**. WaveDrom is
the standard notation for both, and both are authored as data rather than drawn as pictures, so
they stay editable and reviewable.

No Docusaurus WaveDrom plugin exists on npm — verified 2026-08-18. This is a small custom
plugin, following the build-time-SVG pattern the repository already uses for `Icon`.

### Verified behaviour

Spiked 2026-08-18 with `wavedrom@3.6.2`:

- `wavedrom.renderAny(index, obj, wavedrom.waveSkin)` followed by `onml.stringify()` produces
  complete SVG in plain Node, with no browser and no JSDOM.
- `renderAny` dispatches on the object's key: `signal:` produces a waveform, `reg:` produces a
  bit-field strip. One code path covers both needs.
- A three-signal waveform is ~46 KB raw / **3.8 KB gzipped**; ~40 KB of the raw size is the
  reusable skin `<defs>` and `<style>` block, which compresses away. Ten diagrams on one page:
  458 KB raw / **36 KB gzipped**. Acceptable for GitHub Pages, which serves compressed.
- A register diagram is ~3.7 KB raw and carries no skin block at all.

### The MDX-v3 trap (must not be reintroduced)

**Do not emit the SVG as an mdast node of `type: "html"`.** MDX v3 parses raw HTML as JSX. The
WaveDrom skin embeds a `<style>` block containing CSS such as `text{font-size:11pt}` — MDX reads
the `{` as the start of a JSX expression, and the build fails. `style="..."` string attributes
are invalid JSX for the same reason.

The plugin therefore emits an `mdxJsxFlowElement` node naming the `WaveDrom` component, passing
the SVG string as an attribute. The component injects it with `dangerouslySetInnerHTML` — the
identical approach `src/theme/MDXComponents.js` already uses for `Icon`.

### `src/plugins/remark-wavedrom.js`

ESM remark plugin. For each `code` node whose `lang` is `wavedrom`:

1. `JSON5.parse(node.value)`. On a parse error, throw with the source file path and the offending
   snippet — a silent skip would ship a blank diagram.
2. Render to an SVG string as above. Use a per-file counter as the `renderAny` index so the
   generated element ids stay unique within a page.
3. Read an optional caption from the fence meta: ` ```wavedrom title="SPI mode 0 transfer" `.
4. Replace the node with an `mdxJsxFlowElement` named `WaveDrom`, with attributes `svg`,
   `caption`, and `alt`.

`alt` is required for accessibility. Author it in the fence meta as `alt="..."`; if absent, fall
back to the caption, and if both are absent fail the build rather than shipping an unlabelled
diagram.

### `src/components/WaveDrom/index.js`

Renders a `<figure>` reusing the existing `.kb-figure` / `.kb-figure__plate` classes from
`src/css/custom.css`. WaveDrom's default skin is black strokes on transparent — exactly the case
the light plate already exists to solve, as documented in `src/components/Figure/index.js`. No
new dark-mode CSS is required.

The alternative — rewriting the skin's hardcoded hex colors to CSS custom properties in the
plugin — is **not** adopted in Phase 1. The class list is small and fully enumerable (`text`,
`.s1`–`.s16`), so it remains available as a later refinement if the light plate proves visually
disruptive in dark mode. Do not attempt a `filter: invert()` fallback; it destroys the pastel
data-box fills that carry meaning.

### Authoring rules

- Timing diagrams belong on pages where *when* matters. A bus page without a waveform is
  incomplete; a page about linker scripts does not need one.
- A register bit-field strip is always paired with a semantics table giving each field's meaning
  and reset value. The strip shows shape; the table carries the content, and the table is what
  the offline search indexes.
- Keep waveforms under about eight signals. Split a longer transaction into two diagrams.
- At most two or three waveforms per page. Bit-field strips are far smaller and are not capped.

## Page conventions

### Frontmatter

Every topic page:

```md
---
id: <kebab-case-id>
title: <Human Title>
sidebar_label: <short label>
sidebar_position: <int, order within its folder>
tags: [embedded, <area-tag>, <topic-tag>, <topic-tag>]
---
```

- `tags` always begins with `embedded`. Cortex-M pages add `cortex-m`; folder 07 pages add
  `rtos` plus the kernel slug (`freertos`, `zephyr`); folder 10 pages add `linux`; folder 12 adds
  `safety`; folder 13 adds `security`; folder 15 Rust pages add `rust`.
- `id` is required on topic pages, omitted on `readme.md`.
- `sidebar_position` starts at 1 within each folder.

### Folder `_category_.json`

Every numbered folder gets one, indented to match the existing files in `docs/gpu-computing/`
(two spaces):

```json
{
  "label": "<Label>",
  "position": <int>,
  "link": {
    "type": "generated-index"
  }
}
```

`position` equals the numeric folder prefix + 1, so `00-overview` is position 1.

### Page structure

1. `# H1` matching `title`.
2. **Mental model before mechanism.** One or two paragraphs framing what problem this solves and
   why the hardware behaves this way. No page opens with a code block, a register table, or a
   definition list.
3. `:::info[Prerequisites]` — one line with links — only where a page genuinely depends on an
   earlier one. Not on every page; it is a signal, not furniture.
4. `##` sections per subtopic, `###` sparingly.
5. **At least one visual anchor per page**: a WaveDrom diagram, a Mermaid diagram, a `<Figure>`,
   or a substantive comparison table. A page with no visual anchor is flagged in review.
6. At least one `:::warning` naming the specific mistake that costs a day — floating I2C
   pull-ups, `|=` on a two-bit field, kicking the watchdog from a timer ISR, a missing `volatile`,
   a stack sized by guesswork.
7. `## See also` — 3–5 relative markdown links: siblings first, then cross-folder, then the
   section `readme.md`.
8. `## References` — external sources, annotated. See below.

### Admonitions

The same four types the rest of the knowledge base uses. Do not invent new ones.

| Admonition | Use for |
|---|---|
| `:::info[...]` | Framing the problem a feature solves; prerequisites |
| `:::note[...]` | Side facts, part-family and silicon-revision caveats |
| `:::tip[...]` | Practical guidance, rules of thumb, bench technique |
| `:::warning[...]` | Pitfalls, correctness traps, hardware you can damage |

A recurring `:::note` across the section is **part-specificity**: register names, memory maps,
and peripheral counts differ between STM32 families and differ again on other vendors' Cortex-M
parts. Pages state which reference manual a concrete number came from.

### Visual vocabulary

Each tool has exactly one job, so pages stay predictable:

| Tool | Used for |
|---|---|
| WaveDrom `signal` | Anything with time on the x-axis: bus transactions, interrupt latency, DMA transfer phases, wake sequences |
| WaveDrom `reg` | Register bit-field strips |
| Mermaid | Structure, state, and decisions: boot chains, task-state machines, layering, driver FSMs, decision flows |
| `<Figure>` | Real things a drawing cannot convey: board photos, logic-analyzer captures, published vendor block diagrams, Yocto layer stacks |
| `<Tabs>` | Two or three genuine alternatives side by side: register-level vs HAL, STM32 vs RISC-V, FreeRTOS vs Zephyr, C vs Rust |
| Table | Comparison and enumeration: sleep-mode currents, bus trade-offs, MISRA rule categories, register field semantics |

Per CLAUDE.md, a properly-sourced real figure beats a drawn diagram when it shows something a
diagram cannot, and a good diagram beats a bad or irrelevant image. The two combine well — a
Mermaid schematic labelling the mechanism beside a photograph of the actual board.

`<Tabs>` comes from `@theme/Tabs` in `preset-classic` and is currently used by no page in
`docs/`. **Register `Tabs` and `TabItem` globally in `src/theme/MDXComponents.js`** alongside
`WaveDrom`, exactly as `Icon` and `Figure` already are. Every page then stays a plain `.md` file
with no import line, which keeps the section uniform and avoids a mixed `.md`/`.mdx` tree.

### Code

- C in ` ```c `, C++ in ` ```cpp `, Rust in ` ```rust `, ARM assembly in ` ```armasm `.
- Device tree, Kconfig, and linker scripts in ` ```text `.
- Register-level examples target STM32 with CMSIS device headers. Where a HAL call is the
  realistic production choice, show both in a `<Tabs>` block rather than pretending one exists.
- Examples are complete enough to compile where practical; elided bodies use `/* ... */`, never
  pseudocode.
- Every timing or current-consumption number states the part and the conditions it came from,
  and cites the reference manual or datasheet section.

### Images

```
static/img/embedded/<folder-slug>/<name>.png
```

Referenced through the `<Figure>` component with a `/img/embedded/...` path — **no**
`/knowledge-base` prefix; `useBaseUrl` prepends `baseUrl` itself.

Every file gets a row in `static/img/embedded/SOURCES.md` with `file`, `source_url`, `publisher`,
`retrieved`, and `notes`, mirroring `static/img/gpu/SOURCES.md`. Notes must say if an image is a
crop, a frame from an animation, or a screenshot of a UI.

**Preferred sources, in order:**

1. **Bootlin training materials** — CC BY-SA licensed, technically excellent, and the best
   license-clean source for embedded Linux figures. Attribute the license in the caption.
2. **Wikimedia Commons** — for electronics fundamentals, connector photos, and standard
   waveforms; carries explicit license metadata.
3. **Vendor primary documentation** — ARM Developer, ST reference manuals, kernel.org. Copyrighted
   but republished narrowly with attribution, as the GPU section already does with NVIDIA figures.
4. **Own photographs** of the recommended hardware, where a photo is what's needed.

Never substitute a blog or image-host copy to have a figure. If no properly-sourced figure
exists, use Mermaid or WaveDrom — that is the correct outcome.

Watch total size. `static/img/gpu/` is ~1.2 MB for 129 pages; `static/img/embedded/` should stay
in the same order of magnitude. Downscale or crop rather than shipping a multi-megabyte
screenshot.

### External references

Every topic page ends with `## References`: **2–6 entries**, each annotated with why a reader
would click it. Bare URLs are not acceptable. Tiered, in this order:

1. **Primary** — the authoritative document. The Arm Architecture Reference Manual, the ST
   reference manual for the part, the FreeRTOS or Zephyr documentation, `kernel.org`, the standard's
   own designation (`IEC 61508-3:2010`), an RFC.
2. **Canonical secondary** — books and long-form treatments.
3. **Interactive or video** — where watching genuinely beats reading, as with signal behaviour on
   a scope.

Where a source is paywalled or a purchase, say so in the annotation.

The section `readme.md` carries a curated master list, drawn from:

- Joseph Yiu, *The Definitive Guide to Arm Cortex-M3 and Cortex-M4 Processors* / *…Cortex-M0 and
  Cortex-M0+* — the reference for the core.
- Elecia White, *Making Embedded Systems* — the best first book on the discipline.
- Miro Samek, *Modern Embedded Systems Programming* video course — free, register-level, exceptional.
- Memfault's **Interrupt** blog — the best current writing on firmware debugging and fault analysis.
- Jack Ganssle's essays — watchdogs, stacks, and reliability.
- Bootlin's free training materials — embedded Linux, kernel, and Yocto.
- Nordic DevAcademy — BLE, done properly.
- Ben Eater — signalling from first principles on a breadboard.
- ARM Developer documentation, ST reference manuals, `docs.zephyrproject.org`,
  `freertos.org`, `docs.kernel.org`, `docs.yoctoproject.org`, `docs.rust-embedded.org`.

### Safety-standard accuracy guardrail

IEC 61508, ISO 26262, DO-178C, and IEC 62304 are paywalled documents. Folder 12 pages explain
each standard's **structure, intent, and day-to-day engineering consequences**, cite parts and
clause numbers so a reader with access can navigate, and state the purchase cost. They must not
purport to reproduce normative text, and must not be written so a reader could mistake the page
for the standard. Each page carries a `:::note` to that effect.

## Delivery

Three phases. **Each phase is a separate implementation plan** produced by the writing-plans
skill, and each ends with a passing `npm run build`. The section is navigable and coherent at the
end of every phase — no phase leaves dangling links, because `onBrokenLinks: "throw"` would fail
the deploy if it did.

| Phase | Contents | Pages |
|---|---|---|
| **1 — Foundation and first light** | All site wiring (WaveDrom plugin and component, `MDXComponents` registration, image-zoom, sidebar, navbar, Prism languages, `SOURCES.md`), `readme.md`, folders 00–04 | 51 |
| **2 — The working engineer** | Folders 05, 06, 07, 09, 11 | 55 |
| **3 — Systems and shipping** | Folders 08, 10, 12, 13, 14, 15 | 61 |

**Forward links between phases are the one thing to watch.** A Phase 1 page that wants to link to
`07/why-an-rtos` cannot, until Phase 2 exists. Rule: a page may only link to pages in its own
phase or an earlier one. Where a forward reference is genuinely valuable, the earlier page names
the topic in prose without a link, and the later phase adds the link when the target lands.

Phase 1 is ordered so the infrastructure is proven before bulk writing begins: build the WaveDrom
plugin and get one diagram rendering in a production build **first**, then write pages.

Commit as you go, per CLAUDE.md — one commit per self-contained change, `<type>: <what>` on one
line, no `Co-Authored-By` trailer.

`npm run build` is the correctness gate; there is no test suite. In addition to it passing:

- Every image referenced from a page has a row in `static/img/embedded/SOURCES.md`.
- Every page has frontmatter with `id`, `title`, `sidebar_label`, `sidebar_position`, and `tags`.
- Every page has at least one visual anchor and a `## References` section.
- `npm run lint` and `npm run typecheck` pass (the new plugin and component are JS the linter sees).

  dark theme, and at mobile width.

  (~1.2 MB).

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| WaveDrom SVG breaks the MDX build | Root cause identified and specified: emit `mdxJsxFlowElement`, never a raw `html` node. Phase 1 proves it before any page depends on it |
| `image-zoom` conflicts with `ideal-image` | Analysis says they do not overlap (`<Figure>` bypasses webpack image processing). Verified explicitly in Phase 1 against a production build |
| Page HTML grows large from inlined SVG | Measured: 3.8 KB gzipped per waveform. Cap waveforms at roughly two or three per page; if it ever matters, emit the skin `<defs>` once per page |
| Safety-standard pages drift into pretending to be the standard | Explicit guardrail and a per-page `:::note`; pages cite clause numbers and state the standards are purchases |
| Figures with unclear licensing | Sourcing order fixed with Bootlin CC BY-SA first; `SOURCES.md` row mandatory; Mermaid or WaveDrom is the correct answer when no clean figure exists |
| Duplication with the CS section | Normative no-duplication table, checked before drafting any page whose subject appears in it |
| Concrete numbers going stale | Every number cites its part and reference manual section; context7 verification recorded per folder |
| 174 pages is a lot of surface for one reviewer | Three phases, each independently reviewable and independently useful |

## Out of scope

- Editing existing `computer-science/` or `programming/` pages to add forward links.
- Any FPGA, HDL, or hardware-design content beyond what folder 01 needs to explain firmware
  behaviour.
- A companion firmware repository with compilable examples. `remark-code-import` exists and would
  let pages embed code from build-tested sources; adopt it only if a firmware example repo is
  created later.
- Generating register bit-field diagrams from CMSIS-SVD files. More accurate than hand-authored
  WaveDrom `reg` blocks and worth revisiting if register documentation errors show up in practice,
  but a heavy build step for the value in Phase 1.
- Embedding third-party simulators such as Wokwi. The site is otherwise fully offline-capable —
  local search, bundled icons, no external requests — and an iframe would break that property.
  Link out instead.
