# Design: GPU & Accelerators documentation section

## Goal

Add a new top-level documentation section covering GPU and NPU programming, with CUDA as the
spine and real coverage of vendor-neutral portability layers and inference accelerators. The
section is `docs/gpu-computing/`: 14 numbered folders, 128 topic pages plus a section
`readme.md`, plus 14 `_category_.json` files.

This document specifies the structure, conventions, and a page-by-page outline detailed enough
that writing the actual `.md` content is a mechanical follow-the-outline exercise.

## Precedent

Two existing doc sets define the house style at this depth: `docs/programming/boost/`
(16 numbered subfolders) and `docs/machine-learning/` (8 numbered subfolders, its own top-level
sidebar). This section follows the **machine-learning model** — its own top-level sidebar and
navbar tab, numbered folders, `readme.md` landing page — with the boost page conventions
(frontmatter shape, `## See also`, admonition vocabulary).

## Decisions taken

| Decision | Choice |
|---|---|
| Placement | New top-level section + navbar tab (peer of Programming / CS / ML) |
| Scope | CUDA-deep (~65% of pages) + portability layers + NPU/inference accelerators |
| Code language | CUDA C++ primary; Python (CuPy / Numba / Triton / PyTorch) confined to folder 08 |
| Visuals | Downloaded vendor images in `static/img/gpu/` with attribution, plus Mermaid for structural diagrams |
| Currency | CUDA 13.x semantics, verified against the live NVIDIA guide via context7 |

**There is no Prism grammar for CUDA.** `node_modules/prismjs/components/` has `cpp`, `glsl`,
`hlsl`, `wgsl`, `llvm`, `nasm` — no `cuda`. All CUDA code fences therefore use ` ```cpp `, which
`prism-react-renderer` bundles by default and which the existing C++ section already relies on.
No entry for CUDA is needed or possible.

for WebGPU):

  "bash", "cmake", "csharp", "glsl", "hlsl", "ini", "json", "python", "wgsl",
],
```

them.

## Page conventions

### Frontmatter

Every topic page:

```md
---
id: <kebab-case-id>
title: <Human Title>
sidebar_label: <short label>
sidebar_position: <int, order within its folder>
tags: [gpu, <area-tag>, <topic-tag>, <topic-tag>]
---
```

- `tags` always begins with `gpu`. CUDA pages add `cuda` second. Folder 11 pages use the
  vendor/API slug (`hip`, `sycl`, `opencl`, `vulkan`, `metal`, `webgpu`); folder 12 pages use
  `npu` plus the stack slug (`tensorrt`, `onnx`, `tpu`, `openvino`).
- `id` is required on topic pages, omitted on `readme.md` (matching `boost/readme.md`).
- `sidebar_position` starts at 1 within each folder.

### Folder `_category_.json`

Every numbered folder gets one, tab-indented to match existing files:

```json
{
	"label": "<Label>",
	"position": <int>,
	"link": {
		"type": "generated-index"
	}
}
```

`position` equals the numeric folder prefix + 1 (so `00-overview` is position 1).

### Page structure

1. `# H1` matching `title`.
2. 1–2 paragraphs of prose framing **what problem this solves**, before any API detail. No page
   opens with a code block or a definition list.
3. `##` sections per subtopic, `###` sparingly.
4. Ends with `## See also` — 3–5 bullets of relative markdown links, siblings first, then
   cross-folder, then the section `readme.md`.

### Admonitions

Same four types and semantics as the existing sections — do not invent new ones:

| Admonition | Use for |
|---|---|
| `:::info[...]` | Framing the problem a feature solves |
| `:::note[...]` | Side facts, version/compute-capability caveats |
| `:::tip[...]` | Practical guidance, rules of thumb |
| `:::warning[...]` | Pitfalls, correctness traps, performance cliffs |

Compute-capability gating is a recurring `:::note` — e.g. thread block clusters and distributed
shared memory require CC 9.0+, independent thread scheduling requires CC 7.0+.

### Code

- CUDA C++ in ` ```cpp `. Kernels are complete and compilable where practical; elided bodies use
  `// ...` rather than pseudocode.
- Error checking is shown once, in `06-cuda-runtime-and-apis/error-handling-and-checking.md`, via
  a `CUDA_CHECK` macro. Other pages use that macro without redefining it.
- Python examples only in folder 08 and `03-cuda-programming-model/installing-the-cuda-toolkit.md`.
- Every performance claim on an optimization page states the hardware generation it applies to.

### Diagrams

Mermaid (` ```mermaid `, already enabled site-wide) for anything structural: grid/block/warp
mapping, memory hierarchy trees, stream/event timelines, pipeline stages, compilation flow,
collective-communication topologies. Mermaid is theme-aware and carries no license question.

Escape edge labels — an unescaped label broke a build before (commit `958a2e6`).

## Images

Downloaded vendor figures live at:

```
static/img/gpu/<folder-slug>/<name>.png
```

Referenced from Markdown with the `baseUrl` prefix:

```md
![SM architecture](/knowledge-base/img/gpu/02-gpu-hardware-architecture/sm-anatomy.png)
*Source: [NVIDIA Hopper Architecture Whitepaper](https://resources.nvidia.com/...)*
```

Every image carries an italic source caption immediately below it, linking the origin page.

### `static/img/gpu/SOURCES.md`

A manifest, updated whenever an image is added:

| Column | Content |
|---|---|
| `file` | path relative to `static/img/gpu/` |
| `source_url` | page the image was taken from |
| `publisher` | NVIDIA, AMD, Khronos, Google, … |
| `retrieved` | ISO date |
| `notes` | license/terms observed, if stated |

These are third-party copyrighted figures republished from a public GitHub Pages site. The
manifest exists so any figure can be located, re-sourced, or removed on request without hunting
through 125 pages. Prefer Mermaid whenever a diagram can be expressed structurally; reach for a
downloaded image only for die shots, block diagrams too dense for Mermaid, Nsight UI screenshots,
and published benchmark/roofline plots.

## Content currency

Verified against the live CUDA C++ Programming Guide (via context7, 2026-08-13). The section
documents current CUDA, not the CUDA-10-era material most tutorials repeat:

- **Thread block clusters** (CC 9.0+) as a first-class level of the execution hierarchy, launched
  with `cudaLaunchKernelEx` + `cudaLaunchAttributeClusterDimension`, or declared with
  `__cluster_dims__`.
- **Distributed shared memory** — `cluster.map_shared_rank()`, `cluster.sync()`, the histogram
  pattern as the canonical example.
- **Tensor Memory Accelerator** (CC 9.0+) for multi-dimensional global→shared transfers.
- **`cuda::memcpy_async` / `cg::memcpy_async`** and `cuda::barrier` for software pipelining
  (asynchronous from CC 8.0+).
- **Cooperative Groups** as the modern replacement for raw `__syncthreads()` idioms.
- Architecture coverage through **Blackwell**; `__shfl_sync`-family intrinsics only (the
  non-`_sync` variants are removed, not merely deprecated).
