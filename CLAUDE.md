# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Git commits

Commit as you go — after each self-contained change, not batched at the end of a session.

- Message style: short and concise. `<type>: <what>` on one line (`fix:`, `feat:`, `docs:`, `chore:`, `refactor:`).
- No body unless the change genuinely needs it. No bullet list of every file touched.
- **Never** add a `Co-Authored-By` trailer or a "Generated with Claude Code" line.

## What this is

A personal knowledge-base documentation site built with **Docusaurus 3.9** (React 19, Node ≥20). Content is Markdown under `docs/`; the rest is a customized Docusaurus theme. Deployed to GitHub Pages at `https://andriisonsiadlo.github.io/knowledge-base/`.

## Shell output: rtk

`rtk` (Rust Token Killer, `~/.local/bin/rtk`) filters and compacts command output before it reaches the model. It is installed, and a `PreToolUse` hook in `~/.claude/settings.json` (`rtk hook claude`) **rewrites Bash commands automatically**. Verified rewrites:

| You type | Actually runs |
|---|---|
| `cat FILE` | `rtk read FILE` |
| `head -50 FILE` | `rtk read FILE --max-lines 50` |
| `grep -rn ...` | `rtk grep -rn ...` |
| `ls -la`, `find`, `wc -l`, `curl -s` | `rtk ls` / `rtk find` / `rtk wc` / `rtk curl` |
| `git status`, `git log`, `git diff` | `rtk git ...` |
| `npm run build` / `npm run typecheck` | `rtk npm run ...` |
| `npx docusaurus ...` | `rtk npx ...` |

So **do not type the `rtk` prefix by hand** for those — the hook already did it, and `rtk rtk git status` is not a command.

**What the hook does not catch.** Reach for rtk explicitly here:

- `sed -n '1,20p' FILE` — not rewritten. Use `rtk read FILE --max-lines 20` instead; it is the single biggest source of wasted tokens in this repo, since reading Markdown docs is most of the work.
- Pipelines, heredocs, and `python3 -`/`node` scripts pass through unfiltered. If such a command prints a lot, pipe it: `... | rtk pipe`.

**One trap — the lint gate.** The hook rewrites `npm run lint` to bare `rtk lint` and `npx biome check .` to `rtk lint check .`, discarding the npm script. `rtk lint` speaks ESLint, not Biome: it reported `Lint: No issues found` on `src/lib` while Biome was reporting a real `organizeImports` violation and a formatting diff on the same file. **Never trust a rewritten lint command.** Run it raw:

```bash
rtk run 'npm run lint'      # raw shell, no filter, no rewrite
rtk proxy <cmd>             # unfiltered but still counted in `rtk gain`
```

`npm run build` is the correctness gate and is safe under `rtk npm` — it still fails loudly on a broken link. `rtk gain` shows savings so far; `rtk discover` lists commands still being run the expensive way.

## Commands

```bash
npm install          # install deps (README says `npm run install` — that's a typo, use plain install)
npm run start        # dev server at localhost:3000, hot reload
npm run build        # production build to ./build — ALSO validates links (see below)
npm run serve        # preview the production build locally
npm run clear        # clear Docusaurus cache (.docusaurus) — try this when dev behaves oddly
npm run typecheck    # tsc, no emit
npm run lint         # biome check  (lint, not auto-fix)
npm run format       # biome format --write
```

There is no test suite. The closest thing to a correctness gate is `npm run build`: `onBrokenLinks: "throw"` in `docusaurus.config.js` means a broken internal link **fails the build** (and therefore the deploy). Run a build before assuming doc/link changes are safe.

## Linting/formatting

**Biome is the configured tool** (`biome.json`), 2-space indent, applied to JS/TS/JSON/MD. A `.prettierrc` also exists but only carries `prettier-plugin-tailwindcss` for class sorting in editors — the npm scripts use Biome, not Prettier.

## Content architecture

This is the part that requires reading multiple files to understand:

- **`docs/` → sidebars.** Six top-level folders each map to one autogenerated sidebar in `sidebars.js`: `programming`, `game-development`, `computer-science`, `data-tools`, `machine-learning`, and `linux` (see its own section below). Sidebars are `{ type: "autogenerated", dirName: ... }`, so **folder structure on disk *is* the navigation** — you don't hand-edit nav. Algorithms now live under `docs/computer-science/algorithms/` rather than as a separate top-level section. The navbar items that surface these sidebars live in `docusaurus.config.js` (`themeConfig.navbar.items`).
- **`_category_.json`** in a folder sets that folder's sidebar label, `position` (ordering among siblings), and `link` (usually `generated-index` for an auto landing page). Numeric folder prefixes like `00-overview/`, `01-toolchain-and-build/` exist only to order folders on disk; the displayed label/order comes from `_category_.json`.
- **Doc frontmatter** drives per-page nav: `id`, `title`, `sidebar_label`, `sidebar_position`, `tags`. `sidebar_position` orders pages within their folder.
- **Markdown features in use:** Mermaid diagrams (```` ```mermaid ````, enabled via `@docusaurus/theme-mermaid`) and Docusaurus admonitions (`:::info`, `:::note`, etc.). `additionalLanguages` for Prism are `bash`, `cmake`, `csharp`, `glsl`, `hlsl`, `ini`, `json`, `python`, and `wgsl` — using another language in a code fence needs it added to `prism.additionalLanguages` in the config.
- **Live code blocks:** `@docusaurus/theme-live-codeblock` is registered in `themes`. A fence tagged ```` ```jsx live ```` renders an editable react-live playground instead of a static block. Only for React/JSX — everything else stays Prism-highlighted. Keep live blocks small; each one ships its own runtime editor to the client.
- **Figures are preferred over Mermaid diagrams.** When a real figure, photo, or screenshot would show the thing better than a drawn diagram, use one — a picture of actual hardware, a real profiler screenshot, or a published vendor figure carries information a hand-drawn box-and-arrow diagram cannot. Mermaid is still the right tool when the content is genuinely structural (object models, pipelines, decision flows, call graphs) or when no properly-sourced figure exists; a good diagram beats a bad or irrelevant image. The two also work together: a schematic that labels the mechanism next to a figure that shows the real thing is often better than either alone.
  - **Provenance is not optional.** Every third-party image needs a row in `static/img/gpu/SOURCES.md` (source URL, publisher, retrieval date, notes) and an italic source caption on the page directly beneath it. Prefer the vendor's own documentation; never substitute an image from a blog or image host just to have a figure. If no properly-sourced figure exists, use Mermaid — that is the correct outcome, not a fallback to apologize for.
  - **Be accurate about what an image is.** If it is a frame extracted from an animation, or a crop, say so in the `SOURCES.md` notes. Someone re-sourcing it later depends on that.
  - **Watch the file size.** All images under `static/img/gpu/` together total ~1.2 MB. This deploys to GitHub Pages, so a single multi-megabyte GIF or screenshot is not an acceptable trade for one figure — extract a representative frame or downscale instead.
  - Reference images as `/img/<path>/<name>.png` with **no** `/knowledge-base` prefix; Docusaurus prepends `baseUrl` itself.
- **Search** is local/offline via `@easyops-cn/docusaurus-search-local` (no external service); it indexes `docs/` at build time automatically.

## Linux & Kernel Internals section (`docs/linux/`)

A plugin-backed section with its own validation and tooling, built in phases. Phase 1a delivered the infrastructure and a 46-page scaffold. Phase 1b wrote folders `00`–`04` in full (47 written pages total) plus the three `computer-science/` backfill pages (`privilege-levels-and-protection.md`, `exceptions-traps-and-interrupts.md`, `os-structure-monolithic-microkernel-hybrid.md`) those folders depend on — `npm run check:linux -- --written` is the gate that folders 00–04 now pass. Folders `05`–`19` remain scaffolded only in the design spec, not on disk, so no page may link into them yet. Read `docs/superpowers/specs/2026-08-28-linux-kernel-docs-design.md` for the full design; this is the operational summary.

- **The prerequisite graph is enforced, not decorative.** Every doc under `docs/linux/` must carry a `prerequisites: []` front-matter key (empty array is fine, a missing key is not). `src/plugins/knowledge-graph-plugin.js` calls the pure `buildGraph()` in `src/plugins/knowledge-graph/buildGraph.js` at build time and **fails the build** on a missing key, an unresolvable prerequisite/related id, or a dependency cycle — the same `onBrokenLinks: "throw"` philosophy applied to the knowledge graph instead of links. The graph is published as global data under the key `"knowledge-graph-plugin"`, read via `usePluginData("knowledge-graph-plugin")`.
- **A doc's real `id` strips its numeric folder prefix; `node.folder` does not.** Docusaurus's default `numberPrefixParser` strips a leading `NN-` from *both* file and folder path segments when computing a doc's `id`/URL slug — so a page physically at `docs/linux/04-kernel-architecture-and-idioms/x.md` has real id `linux/kernel-architecture-and-idioms/x`, **not** `linux/04-kernel-architecture-and-idioms/x`. A `prerequisites`/`related` front-matter value must use the *stripped* form (it's a doc-id reference) or `buildGraph` rejects it as unresolvable. But `node.folder` in the published graph (from `buildGraph.js`'s `folderOf()`) is derived from the *physical* `sourceDirName`, which keeps the numeric prefix — so a folder-granularity consumer of the published graph data would need the prefixed form (`"04-kernel-architecture-and-idioms"`), unlike `id`/`prerequisites`/`related`. These are two different fields with opposite prefix behavior; don't "fix" one to match the other. (No current component actually reads `node.folder` — see the `KnowledgeGraph` removal note below — but `buildGraph.js` still computes and publishes it.)
- **Six MDX components are registered globally** (`src/theme/MDXComponents.js`) for use in any `docs/linux/` page with no import: `Src` (pinned kernel source links, version lives once in `customFields.linuxKernelVersion`), `KernelFacts` (the fixed closing card — Structure/Path/Observe/Trap), `Lab` (hands-on block, throws on an unrecognized `host`), `Video`, `Cast` (asciinema player — dynamically imported inside a `useEffect`, since the library touches `document` at import time; only its CSS is a static import), and `LearningPath` (renders one ordered, numbered, clickable route through the section from an explicit list of steps). A seventh, `PrereqBlock`, is not MDX-registered — it's injected directly by the swizzled `src/theme/DocItem/Layout/index.js` (before/after the article body) and returns `null` for any doc outside `docs/linux/`. **`KnowledgeGraph` was removed** in Phase 1b — the `knowledge-graph-plugin` still builds the graph and still fails the build on a missing/unresolvable/cyclic `prerequisites` entry, but the graph is no longer *drawn*. `roadmap.md` presents curated learning paths via `<LearningPath>` instead, and `PrereqBlock` (above) remains the per-page surface of the same underlying graph data.
- **Cast policy:** `<Cast>` is for sessions where the interaction *is* the lesson — a `gdb`, `bpftrace`, or `perf` session. Ordinary command-and-output material is an annotated ` ```text ` code block instead, and every cast is accompanied by one of those anyway. `static/casts/linux/hello.cast` is a placeholder proving the player works end to end; no real casts have been recorded yet.
- **Figure policy:** `docs/linux/` is exempt from the licence-gating language in "Content architecture" above — the design spec lifts that restriction for this section — but the `static/img/linux/SOURCES.md` provenance row and the on-page `<Figure source= href= />` credit are still required, exactly as `static/img/gpu/SOURCES.md` works for the GPU section. One convention, one exception.
- **The section is manifest-driven.** `tools/linux-docs-manifest.json` is the single source of truth for the page tree (title, front matter, one-sentence stub summary); `tools/scaffold-linux-docs.mjs` turns it into stub `.md` + `_category_.json` files and never overwrites an existing page without `--force` (`_category_.json` files ARE always regenerated — they're manifest-owned, not author-owned). `tools/check-linux-docs.mjs` is the authoring-convention gate the plugin can't express: category descriptions, required front-matter keys, and — for any page whose `:::info[Not yet written]` stub marker is gone — a closing `<KernelFacts />` and a `## References` section. Run `npm run check:linux` after writing a real page.
- **`.mjs` test files** (`scripts/*.test.mjs`) use `node --test` and need `--disable-warning=MODULE_TYPELESS_PACKAGE_JSON` (no `"type"` field in `package.json`, so Node warns on ESM syntax without it) — see `test:kernel-source`/`test:graph` in `package.json` for the exact invocation.

## Theme / React code (`src/`)

- **Path aliases**: `@`, `@components`, `@css`, `@lib`, `@pages`, `@plugins`, `@theme` → corresponding `src/*` dirs. Defined in **two places that must stay in sync**: `src/plugins/webpack-alias.js` (build resolution) and `jsconfig.json` (editor/types). Note `@theme` here points at `src/theme` and overlaps Docusaurus's own `@theme` namespace — `src/theme/` holds **swizzled** Docusaurus components (DocItem, Navbar, Footer, Blog*, Icon, etc.) that override the classic theme.
- **Styling**: Tailwind v4 (wired through `src/plugins/tailwind-config.js` + `postcss.config.js`) plus shadcn/ui primitives in `src/components/ui/` (Radix + `class-variance-authority` + `tailwind-merge`, helper `cn()` in `src/lib/utils.ts`). Site-wide CSS overrides in `src/css/custom.css`.
- **shadcn/ui is CLI-managed.** `components.json` configures it: `new-york` style, `@/components/ui` alias, `cssVariables: true`, and `tailwind.config: ""` because Tailwind v4 is CSS-first (there is no `tailwind.config.js`). Add components with `npx shadcn@latest add <name>` — it is non-interactive only if you answer overwrite prompts, so pipe `yes n |` to keep existing files. Design tokens (`--background`, `--primary`, `--radius`, …) live in `src/css/custom.css`; dark mode works because of `@custom-variant dark (&:is([data-theme="dark"] *))` there, which maps Tailwind's `dark:` onto Docusaurus's `data-theme` attribute. Note that current shadcn components pull the `radix-ui` mono-package rather than per-primitive `@radix-ui/*` deps.
- **Kibo UI `CodeBlock`** (`src/components/kibo-ui/code-block/index.tsx`, installed from the `@kibo-ui` registry) is a Shiki-based multi-file code block with a language switcher, filename icons, and copy button. It does **not** replace Prism for Markdown fences — it is a React component you compose by hand in `.mdx` or in `src/`. It highlights in a `useEffect`, so SSR renders an unhighlighted fallback first. The upstream `server.tsx` (RSC variant) was deleted; Docusaurus has no server components. `SiCss3` was renamed to `SiCss` to match the installed `react-icons` — re-check that if the component is ever re-added from the registry.
- **Custom plugins** (`src/plugins/`): `webpack-alias.js`, `tailwind-config.js`, and `blog-plugin.js`. The classic preset has `blog: false` — the blog is served by the custom `blog-plugin` instead (config block near the bottom of `docusaurus.config.js`).
- Components are a mix of `.js` and `.tsx`; both are accepted.

## Tooling for agents

- **context7 MCP** is available and is the preferred way to look up library documentation — Docusaurus, React, Tailwind, Radix, shadcn/ui, Biome, Shiki, and anything else in `package.json`. Use it before answering from memory or reaching for a web search; this stack moves fast (Tailwind v4 and Docusaurus 3.x in particular broke a lot of older advice). Resolve the library id first, then query the docs. Do not use it for repo-specific questions — for those, read the code.

## Deployment

GitHub Actions (`.github/workflows/deploy.yml`) builds and deploys to GitHub Pages on every push to `master`. Because of `onBrokenLinks: "throw"`, a broken link merged to `master` will break the deploy, not just warn. `baseUrl` is `/knowledge-base/`, so absolute in-repo paths must account for that prefix (prefer relative doc links).
